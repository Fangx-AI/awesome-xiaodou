# 小豆皇帝模拟器 · 百万用户与 100 万 Star 计划

2026 年 11 月 28 日 · 产品目标、团队分工和阶段验收

## 目标

**让用户用一句自然话，把一件真实的事交给小豆。小豆能定第一步，碰到变化会改案，做完知道下一步。**

产品载体是小豆个人 Agent 的明代朝堂角色扮演。三省提供拟案、封驳和交办，六部按需提供专业能力。用户说「朕想练英语」或「这周加班，计划得改」即可。外部执行继续走小豆已有能力、明确授权和真实回执。GitHub README 是公开导览，小豆 App 是首要使用场景。 [小豆官方介绍](https://apps.apple.com/cn/app/id6815582077)

长期分别衡量 **100 万独立用户完成首次真实任务**与 **GitHub 100 万 Star**。前者衡量用起来的人，后者衡量开源传播。可运营的第一阶段目标是 **100 名外部小豆用户开始试用，至少 60 名做成或确认完成首个真实动作**。

## 先服务什么人

- **首批用户**。已经在用小豆、希望安排一个月的个人目标、经常被工作或生活打断的成年人。优先选减肥习惯、健身、自律、英语、留学这五类。首发用一个最容易展示变化前后的场景作主入口。
- **核心时刻**。用户一开始就收到可做的一步；实际情况变化时，原有成果被保留、受影响项能重排；第七天回来看得懂自己真正做过什么。
- **角色扮演的价值**。「皇上」建立身份感，门下的退回和改案提供实质差异。完整角色介绍与御前问签按需展开。涉及健康、录取、支出等决定仍依实际资料与可核证来源推进。
- **扩展假设**。中文小豆先验证。扩大到百万人时，验证哪些人能稳定获得小豆访问，哪些经过验证的中文和多语言 Agent Skills 客户端能继承体验。宿主支持、来源/语言与版本按实测列明。

| 指标 | 计算口径 | 首轮门槛 |

## 阶段目标与放行条件

| 阶段 | 用户变化 | 放行所需证据 | 负责岗位 |
| --- | --- | --- | --- |
| **S0 · 可真实试用** | 第一次打开就能看懂、发一条消息并拿到首步 | 一次小豆真机完整跑通启动、回报与改期；覆盖可用的 iOS/Android 版本并写明受限项。整套回归及三种 README 宽度通过。12 人理解测试 ≥10 通过 | 产品决定主场景，设计做首屏，开发验兼容，心理学专家复核措辞 |
| **S1 · 有人真正做完** | 一批用户做完一步，有人回来修改下一步 | 100 名独立外部用户启动，≥60 首次完成，≥30 次计划变动，改案保真 ≥85%。以同类任务、同版本比较普通小豆和皇帝模式，报告样本数、差值与典型失败 | 产品牵头试用，心理学专家盲审回复，开发修运行问题，设计跟踪入口 |
| **S2 · 找到可重复获客** | 新用户看真实案例后愿意自己试，回来时能找到原任务 | 1,000 名累计经核验完成首步；至少两个不同渠道各带来 ≥100 名完成首步者；按渠道记录来源、完成和回访。发布升级、回滚和反馈入口跑一轮 | 产品与增长试渠道，设计做可分享案例，开发维护发布，专家审场景资料 |
| **S3 · 多人群与开源分发** | 内容不止作者能生产，维护者能处理兼容与反馈 | 10,000 名累计完成首步；五种场景各有公开证据与回归，至少两名经实际贡献核定的活跃维护者，一个经验证的兼容宿主或合规分发合作 | 技术负责人管版本与贡献，产品管覆盖和合作，设计维护多端样式 |
| **S4 · 走向百万** | 语言与宿主覆盖扩大，用户仍能完成任务 | 在 10 万累计完成首步时复核容量、失效率、单场景维护成本及渠道归因，再推进 100 万。若新增自营服务，按观察峰值压测并证明扩容与恢复；纯宿主路径验证分发、支持及回滚能力。Star 逐级核对 1k、10k、100k、1M | 产品/增长管渠道，开发管版本和支持，设计和专家按语言及场景评审 |

阶段门槛决定是否扩大分发。先看有效用户和风险，后看渠道规模。S0、S1 以取得真机权限和试用者为先决，时间以验收达成计。

## 团队如何工作

| 岗位 | 每阶段必须交付 | 首轮主要负责 |
| --- | --- | --- |
| **产品经理** | 目标人群、任务脚本、指标定义、版本范围、可量化验收与发布决定 | 跟 12 人冷读与初用，组织首次 100 人队列，固定一条主入口，维护按影响排序的问题 |
| **开发负责人** | 单一版本的启动规则、宿主能力表、状态与回执规范、构建和回归、紧急修复或撤回路径 | 对比普通小豆与模拟器；实测新对话、原进度续接、授权变化、提醒创建与触发；扩充回归前保留已通过的能力 |
| **心理学专家** | 行为机制的出处、使用边界、实验设计和难例审阅 | 检查每个计划是否有小行动、触发条件、漏做后的恢复办法和实际复盘；复核羞耻化称呼、连续打卡压力、拟人信任与占卜语气。医疗营养事项请对应专业人员复核 |
| **产品设计师** | 用户旅程、README 首屏和视觉规范、窄屏验收、可用性记录 | 只用一个前后改案的故事展示差异，测新人能否找到开局、如何从 GitHub 切到小豆、能否返回续聊。保留三省六部辨识度 |
| **增长与社区负责人** | 可追踪的传播实验、内容授权、贡献者规则、反馈响应 | 真实案例经同意后脱敏，试两类首次用户渠道。内容让用户直接看原案怎么变、点击后做什么，保留不同渠道的分组结果 |

这些是职责席位，可由同一维护者先兼任。有专业审核要求的事项由具备相应资质或经验的人确认。产品每周公布结果与未解决项，开发对权限与执行准确性负责，专家对高影响场景有发布复核权，设计对首次使用盲测负责。每次只同时测试少数变化，避免把首页、启动内容和渠道的影响混在一起。

## 前四周的工作顺序

1. **第 1 周，找出第一个真机断点。** 开两个真机环境测试位，跑一次「给目标 → 收到首步 → 报进展 → 加班改案 → 设测试提醒」。对创建、实际触发、未授权、超时分别记录。保留当前本地候选作为可复跑基准。
2. **第 2 周，冷读和修首用。** 做 12 个真实新手观察，方法固定为手机打开 README、复述、跳到开局、完成首个任务、返回继续。按卡点顺序改首页和指令。选择一段可以取得同意并公开的真实对话示范。
3. **第 3 周，启动外部队列。** 用真实使用需求招募，记录所用版本、入口、任务类别和实际结果。同类任务分配普通小豆或皇帝模式，预先约定比较的三个结果：首步可做、变更后保真、需要追问几次。
4. **第 4 周，按数据决定去留。** 看 7 天完成和首次复访，检查样本及外部操作结果。达 S1 门槛后扩大到 1,000 人；表现弱的用例记录失败并按影响排序修正。没有得到真机资格时继续做低成本兼容、文档和测试材料，现场结论保留待测。

执行材料已经分成[真机首测](field-tests/pilot-s0.md)和[观察者手册](field-tests/pilot-observer.md)。观察者手册包含匿名记录格式、统计命令和口径。

首次使用、续办和传播的行为假设与素材评审标准见[首用与传播设计](experience-and-sharing.md)。

## 传播与分发

- **传播资产**。首页主案例、20–40 秒真实前后对话、五张按场景的单页图、一段能直接粘贴的开场消息。图文先演示「发生了什么变化、小豆改了什么、哪些进度还在」，再用朝堂画面增强识别。
- **渠道分工**。GitHub 负责可复制入口、透明文档与版本。中文小豆社区、创作者和开源圈做初期试用。平台合作及跨宿主扩展作为 S3 后的增长引擎。公开发帖或向第三方发送材料逐件走已有渠道授权。
- **贡献者体系**。把新增玩法规范成来源、触发、交付、失败回退、复跑记录五项，维护者用真实输入复测。国际化优先保留「拟案、退回、交办与回奏」的用户含义，称呼和历史角色可由用户切换。
- **规模证据**。发布提供版本兼容表、变更日志、可回滚下载和独立审查记录。每个阶段继续核算用户是否完成任务以及出现严重权限错误的频率，Star 采用仓库实时计数。

## 当数据不达标

| 情况 | 下一步决定 |
| --- | --- |
| 模拟器比普通小豆只多称呼，改案和续聊结果相近 | 缩短表演台词，强化门下的真实退回条件与尚书的成果汇报，再跑对照 |
| 找得到首页却无法授权或复制进入 App | 优先修进入 App 和失败回退，单独记录宿主访问限制 |
| 看完案例愿意点 Star，却没有更多人完成首步 | 检查承诺、入口与案例是否一致，主推能复现的真实用法 |
| 有趣但影响健康、金钱等判断 | 保持御前问签由用户主动进入，证据、实际计划和传统解读各按各自规则呈现 |
| 有未经授权的外部动作或虚报回执 | 停止扩大对应流程，修确认与核对逻辑，复测通过再恢复 |
