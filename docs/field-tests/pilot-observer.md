# 小豆试用观察与统计

目标是知道用户能否看懂入口、完成第一件真实的事，以及小豆在条件变化后是否改得对。首批两项验收分别是 12 名冷读者与 100 名外部试用者。真机功能测试的固定材料用于核验能力，由用户自选真实任务的七天试用用于衡量完成。

## 冷读 12 人

给从未看过项目的读者同一个 README 版本，记录入口为仓库根页或 README 直达、设备与浏览器视口。先让对方独立阅读，再依次问四件事：这是什么、在哪里使用、怎样开始、涉及发送或提醒时谁确认。观察对方实际找到入口。四项均答对且找得到入口，记录为冷读通过。保留脱敏原话用于改首页。

冷读参与者可以没有小豆 App。观察者开场只说「请打开这页，用自己的话讲讲它是什么，再找到你会点的第一个入口」。关于名字、对象、按哪里复制等问题，等第一次完整反馈后再解释。

评分时分别核对四件事。理解它是帮自己做计划并推进的 Skill，记 `identity`。知道在小豆独立 App 对话里用，记 `where`。能说清复制开局、加自己的目标并一起发送，记 `how`。知道发送或设置提醒由用户确认，记 `confirmation`。实际在页面找到开局入口，记 `found_start`。首次点下载指南也可以，继续观察能否独立找到发送开局的说明。

观察完整且评审前未提示时，填写四项 `answers` 和 `found_start` 的真假结果。读者明确答错或在约定时间里没找到，记录 `false`。因中途退出或记录遗失而无法判断时留空。观察者在评分前解释过关键位置或答案时填 `assisted: true`，这条用于找问题。报告只用完整、未提示的观察判断是否达到 10/12，另列不完整、提前提示以及各项通过数。

从通过的候选构建下载工件。冷读用 `CANDIDATE.txt` 里的 `public_readme`，观察记录填对应的 `public_readme_commit`。如果测的是仓库根页，另外记下打开时的默认分支提交号。同一批按同一个公开首页版本汇总。只看到分支链接的自报先用来找问题，核对提交号后再并入对应批次。 [候选构建](https://github.com/Fangx-AI/awesome-xiaodou/actions/workflows/check-skill.yml?query=branch%3Acodex%2Fs0-pilot) · [GitHub 文件永久链接](https://docs.github.com/en/repositories/working-with-files/using-files/getting-permanent-links-to-files)

[公开冷读入口](cold-read.md)用于自愿参与和未观察反馈。自行反馈单独归类，只有记录了首次反应、入口选择和四项评分的观察才计入 12 人验收。

## 七天自选任务

使用[七天试用页](seven-day.md)收集自愿登记，也可由观察者直接记录。核对开始日期与试用版本，同一人多次登记合为一个试用编号。公开自报和有观察者核对的记录分别保留来源；公开贴先用于发现问题，进入队列前需按同一口径核对。登记后没反馈的真实启动者仍在分母里。

App 试用从工件里的 `seven_day` 开始，记录 `candidate_commit`。`STARTERS.tsv` 为通用开局、生活计划整包和五份分类开局各列一个候选永久链接。把实际复制的文件名记在 `starter`，例如 `life-plans/health.txt`。使用公开首页时，核对复制的文件与 `public_url` 属于同一个提交，且该行标为 `identical`，再并入对应候选批次。标为 `different` 或 `missing` 时，分别核对和记录版本。`pilot` 链接用于固定功能演练。

[下载和开通](../install.md#下载和开通)收集 App 准入问题。记录系统、商店和实际到达的步骤，区分查找、安装、登录、开通和发送。商店网页状态也单独记录。正式发出开局消息前归入准入记录。若后来开始试用，从实际开局日期起算七天。

`channel` 记录用户最早从哪里知道试用，例如 `github`、`community`、`referral`。同一个人只用一个来源；未知留空，汇总归在 `unspecified`。报告逐渠道列出启动和已到期后的完成情况。登记方式另随观察记录保存，GitHub 公开登记不代表用户一定从 GitHub 得知项目。

用户明确说从一张分享卡得知项目或想开始试用时，可在 `shared_scene` 填写一张卡。制定减肥计划、健身、自律阅读、学英语和留学分别对应 `weight`、`fitness`、`reading`、`english`、`study-abroad`。不知道就留空。分享卡、最早的渠道和实际使用的开局分别询问，例如朋友转发了英语卡，用户后来选了通用开局。 [分享卡](../share-cards.md)

1. 记录试用编号、来源渠道、App 版本。用户在独立 App **实际发出**第一条启用消息才算启动。一个人只登记一个编号。
2. 约定一个用户能判断完成的实际动作，例如「练一次会议自我介绍并写下卡点」。个性化计划可以先完成必要立案；记录从开局到首次拿到合格行动的用时和轮次。收到日期与用户明确完成回报后记录。读到建议、助手说准备好了、观察者根据截图猜测，都不计为用户完成。
3. 如果同一件事实际遇到约束变化，记录每位参与者首次真实变化及小豆改后的回复。先核对原先已完成的动作，然后查受影响项和新下一步。已确认发生变化，但回复材料不全时，照样登记这次变化。后续改案可以用于找问题。
4. 记录用户第 6–8 天首次回来查看同一计划并回报进展的日期，以及本次是否由观察者提醒。报告分别显示主动回访和受邀回访。没有观察到回访就留空，已走完第 8 天的启动者仍留在分母。
5. 第 7 天到期后汇总各批次。比较普通小豆与皇帝模式的参与者使用[固定材料](pilot-s0.md)另做对照，保持顺序交替。实际用户、模拟对话和固定材料测试分别登记。

## 保存可复算的结果

在工作区的公开仓库以外保存结构化匿名记录。下方是格式示例；每项评分取值为 `true`、`false` 或在尚不可判断时省略该项。日期用与测试者一致的本地日历。可保留各受试者同意的脱敏证据，统计文件只记录必要字段。

```json
{
  "as_of": "2026-12-08",
  "candidate_commit": "91a7020c67480107c7e7f499d5993abb3cc92f11",
  "public_readme_commit": "84de5d8efc6e6847c39f64b4b67e562fdd093d15",
  "cold_reads": [
    {
      "id": "P-0001",
      "answers": {"identity": true, "where": true, "how": true, "confirmation": true},
      "assisted": false,
      "found_start": true
    }
  ],
  "trials": [
    {
      "id": "P-0001",
      "channel": "community",
      "starter": "life-plans/learning.txt",
      "started_on": "2026-12-01",
      "first_action": true,
      "finished_on": "2026-12-02",
      "change": {"preserved": true, "affected_only": true, "actionable": true},
      "return": {"day": "2026-12-07", "prompted": false}
    }
  ]
}
```

从项目根目录运行 `python scripts/pilot_measure.py <结构化匿名文件路径>`。报告分冷读、首步、已到期七天队列、改案和回访。已到期者明确回报七天内没完成时，在 `no_completion_reported_on` 填回报日期；收到第七天以后才完成的日期，仍填 `finished_on`。到期没收到任何结果时两个字段均留空。不同批次使用各自的版本记录；每次报数附日期、样本数和未反馈数。达标数值只能作为推进依据之一，还需核验真机原生动作的回执和触发，并检查对照试用中实际观察到的问题。 [阶段目标](../Outcome-Roadmap-2026.md)

确认发生真实计划变动时写入 `change`，暂时拿不到任何评分证据时写 `"change": {}`。某一项明确失败就填 `false`，无法判断的项留空。`replanning` 的分母包括全部已确认的变化，只有三项都通过才进分子。`replanning_unscored` 单列证据不足、尚无法确定成败的变化。

`seven_day_by_starter` 分别显示各版本开局的启动人数和到期完成情况。文件无法确定时，省略 `starter`，报告在 `unspecified` 保留该试用。分组描述样本表现，用户自选的开局类型和任务难度都可能不同。

`seven_day_by_shared_scene` 只显示经核对的试用启动和首步完成。GitHub 的页面流量用于观察仓库访问；同一分享页的五个章节链接用于导航，现有流量数据无法分别核对每张卡的访客数或计算各卡的访客转化率。

## 普通小豆和皇帝模式配对评分

每人同一任务在两个新对话各做一轮，尽量交替两种顺序。只要启动了两组对照，即使最后只拿到一组材料也保留一条记录。由没有参与陪同、看不到组别的人评分。

1. 在仓库以外保存一个材料 JSON 数组，每位参与者一条，含 `id`、`order`、共同任务 `task`，以及 `regular`、`emperor` 各自的回复节选字符串。缺一组材料就省略该组。保留相关输入、已知条件与实际回复的先后，去掉姓名、账号、截图、称呼和组别提示，保留退回原因和行动细节。
2. 运行 `python scripts/pilot_blind.py prepare <材料.json> <新目录>`。给评审的文件是 `review.json`，其中每条材料用随机编号，顺序已打乱。观察者保留 `private-key.json`。工具会拦截角色称呼、部门名和人物名。分发前再读一遍节选，检查是否仍有设备界面、措辞、姓名或其他可识别线索。
3. 评审只在每条材料的 `scores` 填下文的评分字段，未观察到的字段留空。恢复时会核对每个随机编号对应的原任务和节选。发现材料需要修正时，回到原始材料重新打包。若回复风格仍可能暴露组别，在结论说明。
4. 评分结束后运行 `python scripts/pilot_blind.py restore <private-key.json> <review.json> <评分结果.json>`。把输出数组放入同批统计文件顶层的 `comparisons`。原始节选、对应表和逐人评分保留在同意的范围内，公开报告使用汇总与获准引用的脱敏案例。

```json
[
  {
    "id": "P-0001",
    "order": "regular",
    "regular": {"first_action": true, "preserved": true, "affected_only": false, "replan_actionable": true, "follow_up_questions": 2},
    "emperor": {"first_action": true, "preserved": true, "affected_only": true, "replan_actionable": true, "follow_up_questions": 1}
  }
]
```

`order` 记录先试哪组，`regular` 是普通小豆，`emperor` 是皇帝模式。首步看是否符合已知约束、能执行且有完成判据。改案三项分别是保留已完成、只改相关项、给可执行下一步。观察到失败写 `false`；未观察到的字段留空。汇总分开报告两组各胜、都通过、都失败、无法配对、先试顺序及配对差值。报告只说明本次样本的观察结果。

`follow_up_questions` 记开局到合格首步出现前，小豆要求用户补答的独立问题数量。一条消息问了两个不同信息就记 2。没有追问记 0；问题数无法观察就留空。开局前为两组约定相同的观察上限，到上限仍没有合格首步时，填 `first_action: false`，照实记已问数量。只在两组都有首步判定和问题数时比较追问数量。结合首步通过率解读，跳过必要立案同样会影响首步评分。
