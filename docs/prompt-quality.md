# 用一个真实场景试提示词

从下面挑一条，在小豆新对话分别试一句普通提问与完整提示词，比较输出是否符合「怎么看成了」。有连接器的任务先用测试数据。只记录自己看到的结果。

## 先测两条主路径

普通小豆与 Skill 分开新建对话，使用相同的输入、资料、账号权限和 App 版本。记录首次追问次数、任务是否实际完成，以及改变条件后是否保留进展。开局测试可先用[首页指令](../README.md#一句话在小豆里开始)，再用完整版复跑并分别记结果。

- **减肥 H01**：[减肥计划指南](weight-first-week.md)说明用户从一句自然话开局时，怎样从了解情况走到制定首周和按实际记录调整。
- **截图日历 11**：先发一张脱敏截图或逐字转录，内容从「周三三点」改成「周四四点」，但不给原消息日期。检查是否先问日期。确认日期后，用测试日历核对执行结果。

若缺少手机、测试账号、授权或回执，对应项保留「未测」或「权限受限」。同样的输入在不同版本的结果分开记录。 [真机结果](field-tests/README.md)

用 `--flow parallel-plans --flow parallel-plans-life` 回放同一对话中的英语和阅读计划。用户只说「刚才又读了一遍」时，核对小豆是否先问是哪件事。补答后，英语第一句累计两遍，纸书仍读到第十页。纸书改到午休时，检查英语仍安排在明晚。最后让两件事争同一段五分钟，检查小豆是否请用户选优先项。

用 `--flow pause-and-close-plan --flow pause-and-close-life` 测暂停、结案与重开。阅读计划暂停时保留两次阅读和第十页；接着收到英语请求就回答英语。结案后等用户主动重开，午饭后有五分钟时接回原书进度。测试里的周五提醒来自虚构的 App 回执，暂停或结案时仅说明此前的状态，无新增或取消提醒的回执。

用 `--flow first-step-stall --flow first-step-stall-life` 核对用户看完计划却没开始的情况。旧版两条开局都忽略了资料可能无法访问。新版先用一个问题核对障碍。知道链接失效后，给一条申请权限的草稿；有了数据且完成第一条发现后，按剩余四分钟写第二条。主开局与生活计划整包各四轮本地回放通过。

用 `--flow replace-goal --flow replace-goal-life` 核对更换目标。旧版收到「改成读项目文档」时直接改了安排，或开始问文档细节。新版先问是替换会议发言计划还是另开一件事。用户确认替换后，保留已写好的开场和练习记录，说明旧安排停排，用十分钟开始读文档。第二天从读过的章节及卡住的词继续。两个开局各四轮本地回放通过。

用 `--flow progress-correction --flow progress-correction-life` 测进度更正。用户先报本周两次阅读、其中一次日期不详。后来提到周三读过时，先问这一回是否已计入两次。用户更正为周三一次后，重发同一条仍记一次；确认周四新增，才把总数记为两次。旧版回放曾直接把周三填进日期不详的那次。

用 `--flow life-weight-follow-through --flow starter-weight-follow-through --flow weight-weight-follow-through` 回放减肥计划的三个入口。用户明确跳过身高、体重和热量记录后，三条路径都按饮食习惯和两个可用时段制定首周安排，保留周一已经做过的一次饮料替换，只改周二的散步。九轮本地回复中八轮首轮通过词句检查，另一轮用「每周日晚上回看」表达周复盘，人工核对后补进检查词。

用 `--flow private-budget --flow private-budget-life` 检查留学预算保密时能否继续推进。两所学校和费用均为虚构。先整理用户给的费用和材料，再沿用用户自己比较出的结果，把超出上限的 A 校移开。B 校只有学费，下一步用十五分钟去学校官网核对杂费和生活费，保留原来的个人陈述初稿。

用 `--flow fitness-adapt-and-stop` 核对健身立案、首周安排、出差改期和新发疼痛。首周只用实际可用的器材，周二完成后只调整周六。模拟周六出现新的膝部刺痛并影响走路，确认小豆先停止会重现疼痛的动作、按实际记为中止，并建议专业评估。

用 `--flow fortune-chat-and-return` 核对首页开局在没有抽签工具时的问签。直接呈第二签固定示例。明确要求随机换签时，按无工具的实际情况提供自选途径。收到用户贴回的签句后按原句解读。五轮本地回放通过。追问学业时沿用同一签；问留学交费时，回到学校官网可以核对的信息。

用 `--flow reminder-withdrawal` 回放提醒预览后撤回，再用原时间说起另一个任务。用 `--case 27-cancel-after-unknown` 核对创建已请求、回执超时的情形。前者应该停止待办动作，后者应说明未核实并指出任务列表。任务卡和触发仍由[真机演练](field-tests/pilot-s0.md#另测提醒是否实际触发)观察。

用 `python scripts/replay_court.py <输出 JSON> --compare` 对照两条流程。两组使用同一个 Codex 模型，依次收到相同的自然话和各自生成的历史回复。皇帝组使用现有开局或完整指令，对照组只接收任务。输出分组保留原文和触发的检查项；人工核对首步、改案保真和追问数量。结果反映这次 Codex 回放，普通小豆与皇帝模式的实际差异留给[真机对照](field-tests/pilot-observer.md#普通小豆和皇帝模式配对评分)。

2026 年 11 月 28 日，各回放一次。英语任务里，两组都保留了已写的第一句，也都把练习改成五分钟；报进度后，皇帝组明确记录读过一次和接下一句时卡住，对照组直接安排明天怎么接。饮食任务里，皇帝组先问情况，对照组第一轮直接推荐菜品和散步频次；两组在收到只做到一次的回报后都把下周目标设为一次。真机对照优先核对首次立案和续办，五分钟改期与低量复盘也要分别记录。
